# Working rules

1. **Roles.** The owner decides the questions and the design. The agent writes code, tests and docs **and runs the checks itself**: the four check commands in `docs/AGENT_BRIEF.md`, the stage commands in `docs/slice_stages.md` and its own deliberate breakages. It fixes what fails and pastes the raw output in its report. The agent never touches `.env`, never runs git except the read-only `git status --short`, never writes a migration by hand, and edits settings or `pyproject.toml` only when the prompt names them. Claude directs: asks the due questions, writes the prompts, reviews the pushed diff and reads the report. Claude does not run pytest or PostgreSQL in its own sandbox.
2. **Questions first.** Before each slice Claude lists the open questions that are due in `docs/open_questions.md` and the design choices of the slice, each with a default. The owner answers "all defaults" or changes some. Only then the prompt is written.
3. **The slice prompt.** One slice is one prompt, two at most when it truly cannot fit. No a/b/c/d splitting. The prompt holds the slice work, its decisions, its tests and its mutation seeds, names the files to read first, and ends with the line "follow `docs/slice_stages.md` with SLICE, MUTATIONS, TESTS". It does not repeat the stages. Prompts give goals, fixed decisions and exact test names, not finished code (exceptions: exact doc text and tiny exact patches).
4. **Stages.** Quick checks on the new and changed test files first. Then the agent writes its own breakages in `tools/mutations/mutations-<SLICE>.json` for the repo's helper `tools/review.py`, runs the whole mutation file once, and then only the survivors with `--only`. The full verification (`python tools\review.py checks` and `python tools\review.py suite 3`) runs once at the end. All the failures of one output are fixed in one batch before the next run.
5. **Survivors** are sorted into test gaps (a focused test added in the survivor round), equivalent breakages (explained and ignored) and tool artifacts (`--reuse-db` hides edits to model constraints).
6. **The report and the two owner blocks.** The agent ends with a short report (about 60 lines, in the order `docs/slice_stages.md` gives) and two blocks it does not run: **A** the commands to verify, and what to look at in the browser when a page changed (the exact URLs or clicks); **B** the exact `git add` file list, `git commit -m "Slice <id>: ..."` and `git push` to `main`. `git add -A` and `git add .` are never used.
7. **After the agent stops** (owner, Windows Command Prompt, repo folder): read the report and the check output it pasted; when the report says a migration is pending (or names one the agent wrote), run `docker compose exec web python manage.py migrate`; then block A; then `git status --short`, the `git add` line, the commit and the push from block B; finally delete the prompt file (`del slice-N-prompt.md`; `slice-*-prompt.md` is listed in `.git/info/exclude`). The owner does not repeat the checks the agent already ran unless the report says one could not run.
8. **Review.** After the owner has pushed, Claude reads the pushed diff from GitHub — money, stock, security and design first — and the agent's report. The agent's breakage run finds test gaps; Claude's review finds design and money bugs that the breakages missed (Slice 44b-1 had one). A bug found in review gets a small fix prompt before the next slice. Never run the review while the agent is working: `python tools\review.py mutate` edits files in place.
9. **A new chat per slice.** When a slice is reviewed the owner may start a new chat. `docs/STATUS.md` and `docs/open_questions.md` are the hand-over, so "Where we are" stays current and short.
10. **A slice is done** when the checks pass, the test count rose by at least the promised number, the full suite passed three times in one `suite 3` run, the breakages are caught or the survivors explained, the docs are updated (decisions, STATUS, open questions, Python recap) and the prompt file is deleted.
11. **Mark** anything about money, stock, security or login as REVIEW CAREFULLY.
